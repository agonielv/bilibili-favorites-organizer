# 收藏夹名称继承与批量恢复

## 需求依据

用户要求新增可选的名称继承、检查影响整理的重复 / 超时等情况，并修复后半程永久逐条移动造成的缓慢。用户进一步明确：新夹多于旧夹时，前面的继承旧名，额外目标使用预览配置的名字。

## 行为

- 在现有规则中新增命名选项，保留原有自定义名称模式。继承模式按左侧所选来源的顺序配对，包含空来源及只保留副本的来源。
- 新旧数量相同：新夹继承原名，旧夹名后追加“旧”。
- 新夹较少：前 N 个新夹顺序继承来源名称，所有旧夹名称保持不变。
- 新夹较多：前 N 个新夹继承全部来源名称，对应旧夹追加“旧”；额外目标使用配置的基础名称与序号。
- 名称变化在只读预览及最终确认中逐项列出。用户确认前不改名、不创建、不移动。
- “旧”名称如发生冲突，添加编号；超过名称长度限制时保留可用前缀并在预览展示完整结果，不隐藏改名。
- 改名保留源收藏夹可见性、简介、封面，重新核对来源名字与实际视频；不确定写入不重放。中断报告实际改过的名字及已创建目标。

## 性能与安全

已复现：一次短暂的部分成功或顺序异常会将 `orderBulk` 永久降级，后面健康的目标从不恢复探测。6000 条单源、6 个目标的健康场景 62 次移动，一次异常可膨胀至约 6000 次。

保留 1.2 秒串行间隔、限流即停、未知写入不重试、完整目标顺序与来源归属核对。通过精确核对后允许有界的小批次恢复，不能把真实的批量上限 1 当成正常接口强行放大。

在完整读取证明目标后缀已经正确时，可只校正有误的前缀；须在每个写入阶段验证保留后缀，不能扫入计划外内容。性能证据必须比较同一数据集、同一后端行为，且核对最终顺序、全部来源和副本保留。

## 实施取舍

采用独立命名计划与已有执行器集成，避免改动分组算法及外部写入重试策略。性能修复在传输器内处理，与命名实现并行；原生 HTML/CSS/JS、已有毛玻璃风格保持一致。未验证的服务端行为不做成功承诺，真实账号操作仍不在本次测试范围。
