# 1.4.0 移动性能与正确性

## v1.4.0：修复后半程永久逐条退化

临时的批量顺序异常或成功响应缺项，旧实现会永久禁用整轮的有序批量。中转成功缺项还会被记录成永久单条上限。现将明确的接口拒绝上限与临时缺项回退分开，在完整核对过的检查点有限度重新探测批量，每个目标最多一次；风险、写入不明确及真实单条上限仍停止或保持保守路径。

目标全量核对发现局部错误时，先读取全部分页确定正确后缀，只将错误前缀返回本轮私密中转，核对保留部分后逐条修复前缀，最后重新完整核对目标和空中转。不是只核对前几条，也不会移动计划外内容。

故障场景执行 `npm run benchmark:recovery`。若要同时复现 v1.3.4 对照，在临时目录导出固定基准后运行：

```sh
mkdir -p /tmp/bfo-v134-baseline
git archive 14af79c extension/lib | tar -x -C /tmp/bfo-v134-baseline
printf '{"type":"module"}\n' > /tmp/bfo-v134-baseline/package.json
BFO_BASELINE_LIB_DIR=/tmp/bfo-v134-baseline/extension/lib npm run benchmark:recovery
```

结果见 [recovery-benchmark.json](recovery-benchmark.json)。每个版本使用相同故障注入与数据，逐 ID 核对所有目标位置、来源已移出和中转为空。6000 条单源的一次部分成功从 6007 次移动降为 117 次，一次乱序从 6010 次降为 193 次；1000 条中仅第 26 / 27 个位置错序时，移动从 1024 次降为 42 次，只重建 27 条前缀，保留正确的 973 条后缀。正常的四组基准不变。

| 故障 / 数据 | 旧版移动 / 执行请求 | v1.4.0 移动 / 执行请求 |
| --- | ---: | ---: |
| 健康单源 6000 条 | 62 / 259 | 62 / 259 |
| 单次目标部分成功，单源 6000 条 | 6007 / 6225 | 117 / 393 |
| 单次目标乱序，单源 6000 条 | 6010 / 6180 | 193 / 424 |
| 首次中转部分成功，三来源 6000 条 | 7000 / 7183 | 1116 / 1473 |
| 只支持单条，单源 6000 条 | 6003 / 6211 | 6003 / 6211 |
| 持续任意乱序，单源 6000 条 | 6004 / 6161 | 6031 / 6278 |
| 持续部分成功，三来源 6000 条 | 7000 / 7183 | 6012 / 6324 |
| 后部两个位置错序，单源 1000 条 | 1024 / 1357 | 42 / 318 |

首次中转异常所在目标仍使用单条移动，第二个从 2 → 20 → 100 重新探测，其余四个从 100 开始。持续任意乱序场景增加了有界探测的少量请求，无法假定每种故障都会加速。

首次异常所在目标可能仍需逐条移动以恢复可证明的归属。接口持续乱序或只接受单条时仍然慢；增加的恢复探测受限，不循环试探。所有数字都是模拟请求量，不是实际服务端耗时。

## 本次完成

已将 1.0.0 永久禁用批量的占位路径替换为**执行时探测、校验、协商、校正和回退**的完整实现。仍遵守用户已确认的优先级：精确排序优先，在此前提下尽量提速。

- 批次从 2 开始，核对后逐步扩大到 20、100；跨目标保留本次已探测状态，不持久化平台能力假设。
- 同一请求只涉及同一来源与目标。来源高度交错时，成本模型选择私密中转，避免每次源变化都退化成一个视频一次请求。
- 最多新建一个本次专用私密中转夹。按目标逐个汇入与清空，每次只持有当前目标的计划视频，容量不超过 1000；所有目标共用该夹。
- 批量参数顺序与展示顺序相反时，观察实际结果，归集已移动项后尝试一次方向校准。任意乱序则先逐条校正；v1.4.0 经完整核对后允许有界恢复探测。
- 明确参数拒绝可能已部分应用：读取真实目标与来源，确认互斥归属，只处理仍在来源的项，再降低上限。递归降批次按照已消费片段推进，不能重复发送重叠片段。
- 成功响应也可能部分应用：中转集合及目标数量 / 顺序核对发现缺项后，先确认缺项的真实来源，再处理；不盲目重放已在目标中的 ID。
- 首次中转探测不支持批量时，核对并返回本次探测中已移动的少数视频，然后放弃中转，避免把整个任务都先逐条中转一遍。
- 只对本次计划内视频做校正。发现计划外内容、重复归属或不明去向即停，不删除、去重或处理他人内容。
- 所有目标最终读取**全部分页**，逐 ID、逐位置对比预览；再核对来源没有遗留计划视频。前几条探测通过不等于完整成功。
- 风控立即停止，不发起后续核对 / 校正请求；写入超时或 HTTP 响应不明确时直接停，不自动重复写入。

## 分页协商

读取首先请求 `ps=100`。明确参数拒绝时仅回退一次到 20；服务器静默截断至 20 等更小页时，从首个实际页大小学习，然后以正确偏移继续。分页中途大小或数量发生变化会停止，避免重复或跳页。不会在风控后换页大小继续请求。

## 中转与确认

最终确认明确说明可能额外创建一个私密中转夹，仅用于用户已确认的任务。成功后保留空夹，用户可在 B 站自行删除。失败或关闭页面时可能有视频停留在源、目标或中转夹，错误提示给出中转名称与 ID；不得把含视频的中转夹当空夹删除。本版仍不提供断点恢复或一键撤销。

## 可重现的 6000 条模拟

命令：`npm run benchmark`。原始记录：[transfer-benchmark.json](transfer-benchmark.json)。

测试使用内存后端模拟接口行为，并按实际分页数计算 API 请求。数据为 6000 条、6 个最终目标、12 位 UP。逐条基线使用每页 20 条；基线和优化均包含执行前来源全量核对、目标全量核对和最后来源核对，不含最初预览扫描；1.3.2 另计每个新目标的空夹检查与每个来源（包括目录显示为零）的最终实际读取。1.2.1 为取消固定过期时限而增加执行前核对，因此执行请求比旧版本增加 60 或 300 次，保留这一安全成本。所有优化场景都逐 ID 核对最终顺序，并断言源记录已移出、中转夹为空。

| 来源 | 接受页大小 | 基线执行请求 | 优化执行请求 | 其中移动请求 | 执行请求减少倍数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 连续 | 100 | 6620 | 264 | 62 | 25.08 |
| 六源交错 | 100 | 6620 | 485 | 136 | 13.65 |
| 连续 | 20 | 6620 | 744 | 62 | 8.90 |
| 六源交错 | 20 | 6620 | 1205 | 136 | 5.49 |

在仅计算 1.2 秒请求间隔、忽略网络时延与首次扫描的模型中，上述执行阶段下界约为 5.26 / 9.68 / 14.86 / 24.08 分钟。**这是节流模型，不是 B 站真实完成时间。** 首次源扫描、网络延迟、错误、顺序校正和降级均需额外时间；不支持批量时仍可能需要数小时。

## 已覆盖的异常模型

- 参数依次写入、参数直接作为展示顺序、任意批内乱序。
- 开头正确但后部乱序，必须由全量核对发现并校正。
- 上限为 1、2、3、4、5、7、12、13、37、100 等；拒绝时可能部分应用。
- 成功响应仅移动部分视频，不允许重复移动已有项。
- 多来源、UP 排列、时间升降序和容量拆分的固定种子 100 组组合。
- 批量 / 核对时出现风控、写入不确定、目标中加入计划外内容、类似复制的响应。

## 真实平台证据边界

公开资料库 `SocialSisterYi/bilibili-API-collect` 和 `Nemo2011/bilibili-api` 当前均已关闭并移除相关资料。本轮只读核查没有取得可保证现行批量上限和排序语义的资料，也没有真实账号。因此实现不硬编码“平台已经保证保序”，而是在用户执行本次已确认任务时逐步观察，并以全量结果作为最终成功条件。

云 Chromium 的管理策略仍禁止加载自定义扩展，未修改该策略。页面模块与扩展 API shim 的模拟集成通过，不等于 Chrome / Edge 本机实装或真实账号验证。请先使用少量测试收藏验证，再逐步增加规模；不需要提供 Cookie 或 CSRF。
